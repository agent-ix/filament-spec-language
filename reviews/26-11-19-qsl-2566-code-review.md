## Summary

Code review (rust-style and rust-review lane) plus a manual AC-to-test gap check of PR #3112. Ticket: QSL-2566. Read-only from `gh pr diff` and a scratch bare fetch of the PR head; nothing was built or run. Confidence "high" means traced by reading.

The PR removes the `ordering_part` node flag (`Node::ordering_part`, `CheckedNode::is_ordering_part`, `NodeSource::is_ordering_part`) and has the evaluator decide ordering parts from the shape of the `and` node it evaluates (`ordering_composition`, `Position`, `Task::EvalAt`/`ApplyPart`). The package reader gains `bounded_domain/float_rounding` parameter types and projects the IEEE `numeric_equal`, `total_order`, `bit_identical`, `negate`, `add`/`sub`/`mul`/`div` and `sqrt` applications. Two TC-3077 tests are un-ignored, and the `sqrt` body of AC-30 moves to its own ignored test.

## Examined scope

- Shape rule (`ordering_composition`): it matches FR-397 "Ordering parts". The match is an `and` of `and(N(x,x), N(y,y))` and either `and(total(x,y), not N(x,y))` or `or(total(x,y), N(x,y))`, where x and y are each one local slot or one float literal. Literal equality is by bit pattern (`IeeeValue` derives `PartialEq` on width and bits), so a NaN literal matches itself. Connective origin is not read, so a hand-written composition qualifies, as FR-397 requires. (examined)
- Position propagation: Ordering -> Parts/Tail, Parts -> Part, Tail -> total_order (plain) plus Part or NotPart -> Part. Short-circuiting is preserved through `Task::Short(node, position)`. Only the three `numeric_equal` nodes reach `ApplyPart`. A node shared with a standalone use is charged by the path that reaches it, which is what AC-31's last clause requires. (examined)
- FR-265 retention: `note_comparison` lost its `is_ordering_part` guard, but the part branch of `apply_as` never calls `note_comparison`, so parts are still not retained. Standalone nodes are retained. (examined)
- Leftover readers and writers of the marker: none at head. `ordering_part` survives only in test names and TC-3077 prose. The marker was never emitted by fsl-package, so package bytes and identity do not change. No compatibility shim was added. No ADR mentions ordering parts. (examined)
- The reader's IEEE arms are strict on arity and rounding mode. Each refusal is a named FR-390 fault (`reader-ieee-*`), and identities the reader does not handle (fma, conversions) still fall through to the unsupported refusal. (examined)
- `node_value_type` float_rounding branch and `float_rounding_type`: see FND-001 and FND-002. (examined)
- Tests: the AC-30 test asserts source == package (outcome and full charge log) for five bodies at p = 1.0 and NaN. The AC-31 test asserts that the hand-written log equals `p < q`'s on both routes, that the near misses are equal across routes with 4 `ieee.operands` each, and that the standalone case is equal across routes and adds exactly one more. Both routes are asserted. (examined)
- `#[ignore]`: there is one new ignore, on the sqrt split, citing QSL-2566 (FND-004). There is no stray ignore. No Python. (examined)
- Reported reds: `x05_ieee_arithmetic_records_flags_and_float_ordering_composes` runs source-route `divide`, `convert` and `negate` plus checker-only `check_in` of `<` and has no connective evaluation. The diff's evaluator change is limited to connective dispatch and the part flag, and its checker change leaves node kinds and types unchanged, so the diff does not plausibly touch this test. The fsl-package `emit/tests/protocol_locations` fixtures (W, E, E-C) contain no float or IEEE operation, and the reader additions trigger only on `filament.op.ieee.*` identities and the `bounded_domain/float_rounding` error form, so the diff does not plausibly touch them either. Neither was confirmed by a run. (examined)

## Verdict

Not mergeable. The evaluator half is correct and matches FR-397 "Ordering parts". The flag is gone with no leftover readers or writers, and both un-ignored tests assert both routes. The reader half has one high defect: the float_rounding type branch types any node whose type merely contains a `Float64[mode]` as the bare float (FND-001). It also turns a malformed float_rounding node into an "unsupported feature" refusal, not a pinpointed fault (FND-002). The sqrt ignore cites the ticket this PR delivers, not a live follow-up (FND-004). The location gap it describes also affects every flag-raising IEEE arithmetic operation the PR adds, and none of those has a package-route test (FND-003).
